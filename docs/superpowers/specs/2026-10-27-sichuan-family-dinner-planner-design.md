| 产品形态 | 手机优先的本地 PWA |
| 使用对象 | 一个三代同堂家庭，3 个大人、1 个小孩 |

## 1. 文档目的

本文档定义第一版产品的目标、使用流程、推荐规则、数据模型、技术方案和验收标准。确认后可直接据此拆分为实施计划。

## 2. 背景与问题

家里请阿姨负责做晚饭，不负责买菜和安排菜单。每天需要解决三个连续问题：

1. 第二天吃什么。
2. 两荤一素如何搭配，避免肉类重复、口味过重或连续吃同一道菜。
3. 菜单确定后，需要买哪些菜，如何把清单交给家人。

现有方式依赖临时思考，容易出现决策拖延、菜品重复、漏买食材和采购清单零散的问题。

这个应用不负责教做菜，也不替代买菜。它负责把“想菜单”和“列采购项”这两步变得足够快。

## 3. 产品目标

- 用户打开应用后，30 秒内可以得到一桌可接受的晚餐菜单。
- 从应用首页到拿到可复制的采购清单，不超过 5 次主要点击。
- 菜单满足两荤一素，肉类有变化，辣度适合包含小孩的家庭。
- 已确认菜单在 7 天内不重复。
- 采购清单自动合并同类食材，并排除家中常备项。
- 菜谱和家庭数据保存在本机，不要求注册账号。
- 手机浏览器可正常使用，也可以添加到桌面离线打开。
- AI 是可选增强能力，不进入离线主流程，也不阻塞选菜和采购清单生成。
- AI 生成的菜单、菜品和食材草稿必须经过用户确认后才能写入本地数据。

## 4. 非目标

第一版明确不做以下内容：

- 不做账号、登录、家庭组和多设备同步。
- 不让 AI 在运行时直接生成最终采购清单。
- 不允许 AI 未经确认修改菜单、菜品或食材数据。
- 不提供医疗建议、疾病饮食方案或精确营养评分。
- 不做精确营养计算、热量计算或健康评分。
- 不记录食材克数，不做按人数换算用量。
- 不提供详细烹饪步骤，默认阿姨会做家常川菜。
- 不接入生鲜平台、不比较菜价、不直接下单。
- 不提供菜谱图片和视频。
- 不实现复杂的库存数量和保质期管理。

这些能力可以在核心流程稳定后再评估。

## 5. 用户与使用假设

- 主要操作者是提出需求的家庭成员，负责决定菜单、安排采购和把清单发给家人。
- 实际执行者包括买菜的家人和做晚饭的阿姨。
- 每顿晚餐有 3 个大人和 1 个小孩。
- 日常菜系以普通家庭川菜为主，不要求餐馆级复杂菜。
- 通常每天买菜，也会储备一部分常用食材。
- 晚餐默认是两荤一素，汤可有可无。
- 采购清单只需要食材名称，不需要数量。
- 一个应用实例只服务一个家庭。
- 应用界面使用简体中文。
- 菜品禁用、忌口和常备食材由用户在本机维护。

## 6. 产品形态

第一版是单页 Web 应用，针对性适配手机屏幕，并通过 PWA 支持安装到桌面和离线使用。

应用没有业务后端。内置菜库随应用发布，自定义菜品、设置、历史菜单和常备食材保存在浏览器本地数据库中。

AI 采用单用户自带的 Key（BYOK）直连模式：用户在设置中填写兼容 OpenAI Chat Completions 的接口地址、模型名和 API Key。Key 只保存在本机 IndexedDB，不写入代码、不写入导出备份。该方式意味着 Key 可能被浏览器开发者工具或恶意扩展读取，仅适用于本机个人使用，不适用于公开部署或多用户环境。

AI 不可用时，本地推荐、换菜、采购清单、历史和数据备份必须保持完整可用。

本地数据必须支持 JSON 导出和恢复，因为浏览器清理数据后本地记录会消失。

## 7. 核心流程

```text
打开应用
  ↓
默认安排明天的晚餐
  ↓
生成两荤一素（汤可手动开启）
  ↓
换一桌，或只换其中一道
  ↓
可选：AI 检查搭配（失败可跳过）
  ↓
确认菜单
  ↓
合并食材并排除常备项
  ↓
复制清单，发给家人
```

生成和换菜阶段只存在于当前页面，不写入历史。只有点击确认后，菜单才成为已确认菜单，并参与后续 7 天去重。

## 8. 功能需求

### 8.1 安排页

- 默认日期为本地时间的明天。
- 用户可以切换到今天或其他日期。
- 页面展示当前日期的菜单状态：未安排、草稿或已确认。
- 已确认菜单再次打开时直接展示，不重新随机。
- 页面提供“安排一下”“换一桌”“就吃这些”三个主要操作。
- “加一份汤”是单独开关，默认关闭。
- 生成后展示两荤一素，每道菜显示菜名、肉类类型、辣度和口味标签。
- 每道菜提供一个“换这道”操作。
- 页面需要展示搭配检查结果，例如肉类不重复、包含清淡菜、辣度符合设置。
- 提供“AI 检查这桌菜”入口，用于补充营养结构和口味建议；AI 建议只展示，不自动应用。
- 如果因为菜库不足放宽了重复限制，页面需要明确提示。

### 8.2 推荐

推荐以整套菜单为单位生成，不采用先随机三道菜再检查冲突的方式。

推荐必须满足第 9 节定义的硬性规则，并在合法组合中做加权随机，避免菜单长期固定。

### 8.3 单道换菜

- 换菜时保持另外两道菜不变。
- 只从与当前菜相同角色的菜品中选择，即荤菜换荤菜、素菜换素菜、汤换汤。
- 新菜不能与已锁定菜品重复。
- 新菜仍需满足肉类差异、辣度上限、忌口和重复天数规则。
- 如果找不到符合条件的菜，按第 9.4 节逐级放宽重复限制。
- 如果仍找不到，提示用户检查菜库、禁用菜品或忌口设置。

### 8.4 确认菜单

- 点击“就吃这些”后，菜单按目标日期保存。
- 同一日期再次确认时覆盖该日期的已确认菜单。
- 已确认菜单重新编辑后，采购清单同步更新。
- 菜单确认时间使用本地时间记录。
- 推荐草稿不进入历史，也不影响下一次推荐。

### 8.5 采购清单

- 采购清单由已确认菜单自动生成。
- 采购清单必须由已保存的菜品食材数据确定性生成，必要时可调用 AI 做补充建议，但 AI 不能成为清单的唯一数据来源。
- 只合并食材名称，不显示重量、数量和规格。
- 食材按分类分组，顺序固定为：肉禽蛋、蔬菜、豆制品、调料、其他。
- 标记为“家里常备”的食材不进入待买清单。
- 页面可以折叠显示被排除的常备食材，方便核对。
- 提供“复制清单”按钮，复制内容可直接粘贴到微信。
- 没有已确认菜单时显示空状态，引导用户先安排菜单。

复制文本格式：

```text
明天晚餐：回锅肉、鱼香茄子、蒜蓉油麦菜

需要买：
五花肉、蒜苗、茄子、油麦菜、蒜
```

### 8.6 菜库

- 首次使用导入用户提供的 180 道菜单，完整名单和归类见 `docs/menus/2026-10-27-sichuan-family-dinner-menu-library.md`。
- 菜库保留原始分区信息，同时使用标准角色、主蛋白质、辣度和口味作为推荐依据。
- 菜品分为 `ready` 和 `draft`：`ready` 才能进入自动推荐；`draft` 可在菜库中查看，但必须先补全食材和角色才能启用自动推荐。
- 内置 `ready` 菜品应覆盖猪肉、牛肉、鸡肉、鱼虾和蛋类，并保证有足够的清淡素菜。
- 支持按角色、肉类、辣度和口味筛选。
- 支持按菜名搜索。
- 用户可以临时停用某道菜，停用后不参与推荐。
- 用户可以新增自定义菜，字段包括菜名、角色、肉类、辣度、口味和食材。
- 自定义菜的食材优先从已有食材库中选择，也允许新增食材。
- 支持上传菜单图片，由 AI 提取菜名和原始分区，生成待确认的导入草稿。
- 支持对 `draft` 菜品调用 AI 补全食材草稿，用户修改并确认后才转为 `ready`。
- 内置菜不可删除，只能停用；自定义菜可以编辑和删除。
- 菜库页面需要显示当前可用菜数量，帮助用户判断是否禁用了过多菜品。

### 8.7 设置

- 常备食材：勾选后不计入采购清单。
- 忌口食材：包含被勾选食材的菜品不参与推荐。
- 重复天数：默认 7 天，允许调整。
- 每餐最多辣菜数：默认 1 道，允许调整为 0、1 或 2。
- 汤默认是否开启：默认关闭。
- AI 服务：启用开关、接口地址、文本模型、视觉模型和 API Key；提供“测试连接”和“清除 Key”。
- 数据导出：下载一个包含设置、自定义菜品和已确认菜单的 JSON 文件。
- 数据恢复：选择合法备份文件后恢复，并在恢复前提示会覆盖当前数据。
- 数据重置：二次确认后清空本地数据，并恢复内置菜库和默认设置。

### 8.8 历史

- 展示最近已确认的菜单，按目标日期倒序排列。
- 每条记录显示日期、菜品和是否包含汤。
- 支持查看某一天使用的采购清单。
- 历史只记录已确认菜单，不记录生成和换菜过程。

### 8.9 数据备份

- 导出文件包含 `schemaVersion`，便于以后升级数据格式。
- 导入时先校验版本和数据结构，校验失败不能覆盖现有数据。
- 备份只包含用户数据，不重复导出内置菜库。
- 恢复自定义菜品时保留其食材关联。
- 备份默认不包含 API Key，也不包含 AI 请求缓存。

### 8.10 AI 辅助

- AI 功能默认关闭，用户配置 Key 后手动开启。
- 支持“检查菜单搭配”：显示营养结构、油腻程度和儿童适宜性的文字建议，不输出疾病或医疗结论。
- 支持“补全菜品食材”：用于自定义菜和 `draft` 菜品，生成可编辑的食材草稿。
- 支持“菜单图片导入”：识别图片中的菜名和原始分区，匹配已有菜名，生成待确认导入列表。
- 支持“批量补全食材”：按小批次处理 `draft` 菜品，结果必须可逐条修改和确认。
- AI 不得自动确认菜单、自动启用菜品、自动删除菜品或自动写入采购清单。
- AI 建议中引用的菜品 ID、食材 ID 必须经过本地校验；不存在的 ID 直接丢弃并提示。

## 9. 推荐算法

### 9.1 输入

- 目标日期。
- 启用中的菜品。
- 已确认菜单历史。
- 家庭设置：重复天数、最多辣菜数、忌口食材、是否加汤。
- 可注入的随机数函数，用于测试和稳定复现。

### 9.2 硬性规则

以下规则必须同时满足：

1. 菜单恰好包含 2 道荤菜和 1 道素菜。
2. 开启汤时，额外包含 1 道汤；未开启时不包含汤。
3. 所有菜品处于启用状态，且不包含忌口食材。
4. 所有菜品不能重复（包含汤）。
5. 两道荤菜的蛋白质类型必须不同。
6. 辣菜数量不超过设置值，默认不超过 1 道。
7. 整桌至少有一道口味为“清淡”的菜。
8. 与目标日期相差不超过重复天数的已确认菜单中，不能出现相同菜品。

第 5、6 条不自动放宽。若满足不了，应用提示用户调整设置或菜库，而不是悄悄生成冲突菜单。

### 9.3 组合评分

满足硬性规则后，对每个组合计算分数：

- 两道荤菜的蛋白质都没有出现在上一顿已确认晚餐中：`+3`。
- 肉类组合未出现在最近 3 顿已确认晚餐中：`+1`。
- 素菜为清淡口味，且至少一道荤菜为重口：`+1`。
- 随机扰动：`+ rng() * 0.5`。

将所有组合按分数降序排序，取前 20 个。分数越高权重越大，按名次使用 `20, 19, ..., 1` 作为权重随机选择一个。这样既保证搭配质量，也不会每天固定推荐同一组。

评分和随机数函数必须可测试。测试时使用固定随机数，生产环境使用浏览器随机数。

AI 搭配检查不参与硬性规则判定，也不能覆盖本地推荐结果。AI 只能基于当前菜库中的有效菜品提出建议，用户手动应用后，仍要重新执行本节的硬性规则校验。

### 9.4 无解时的放宽顺序

1. 按设置中的重复天数过滤。
2. 如果无解，把重复天数缩短为 3 天并提示。
3. 如果仍无解，取消重复限制并提示。
4. 如果仍无解，返回“可用菜品不足”，并给出快捷入口：恢复默认菜库、减少忌口、减少最多辣菜数或关闭汤。

放宽结果需要记录在草稿上，确认后一并保存，用于在历史中解释当时为什么出现近期重复。

### 9.5 单道换菜

单道换菜复用同一套过滤和评分逻辑，只枚举当前菜品角色下的候选项，同时把另外两道已经确定的菜视为锁定项。

换菜后需要重新执行整桌硬性规则检查，不能只检查新菜本身。

### 9.6 历史窗口

历史判断使用已确认菜单，不包含草稿。

对于目标日期 `D`，已确认菜单日期 `P` 只要满足 `abs(D - P) <= repeatDays`，其菜品就进入去重集合。这样既能避免与过去重复，也能避免与已经安排好的未来晚餐重复。

日期使用本地日历日，不使用 UTC 时间截断，避免晚上安排明天菜单时日期错位。

## 10. 数据模型

### 10.1 基础类型

```ts
type DishRole = 'meat' | 'veg' | 'soup' | 'other';
type Protein =
  | 'pork'
  | 'beef'
  | 'chicken'
  | 'duck'
  | 'lamb'
  | 'rabbit'
  | 'fish'
  | 'shrimp'
  | 'frog'
  | 'squid'
  | 'crab'
  | 'crayfish'
  | 'egg'
  | 'other'
  | 'none';
type SpiceLevel = 0 | 1 | 2;
type Flavor = 'light' | 'normal' | 'rich';
type IngredientCategory =
  | 'meat'
  | 'vegetable'
  | 'soy'
  | 'seasoning'
  | 'staple'
  | 'other';
type DishSourceGroup =
  | 'pork'
  | 'beef'
  | 'chicken'
  | 'rabbit'
  | 'seafood'
  | 'cold'
  | 'snack'
  | 'shredded-pork'
  | 'vegetable'
  | 'soup'
  | 'rice'
  | 'unspecified';
type DishDataStatus = 'ready' | 'draft';
```

`SpiceLevel` 含义：`0` 不辣，`1` 微辣，`2` 较辣。

`Flavor` 含义：`light` 清淡，`normal` 适中，`rich` 重口。

### 10.2 食材

```ts
interface Ingredient {
  id: string;
  name: string;
  category: IngredientCategory;
  defaultPantry: boolean;
  isCustom: boolean;
}
```

- `id` 是合并采购清单的唯一依据，不能使用菜名或食材名称字符串合并。
- `defaultPantry` 只对内置调料设置默认值，葱姜蒜等易耗食材默认不设为常备。
- `isCustom` 用于区分内置食材和用户新增食材。

### 10.3 菜品

```ts
interface Dish {
  id: string;
  name: string;
  role: DishRole;
  protein: Protein;
  spiceLevel: SpiceLevel;
  flavor: Flavor;
  ingredientIds: string[];
  sourceGroup: DishSourceGroup;
  dataStatus: DishDataStatus;
  autoPlannable: boolean;
  isCustom: boolean;
}
```

- `role` 是菜单中的位置，必须人工准确分类。
- `sourceGroup` 保留用户菜单图片的原始来源，只用于溯源和筛选，不直接决定推荐角色。
- `dataStatus: 'draft'` 表示食材或分类尚未复核，可以在菜库中展示，但不能进入自动推荐。
- `autoPlannable: false` 表示即使数据完整也不进入自动推荐，例如主食、小吃和待确认菜品。
- 菜品是否启用由 `Settings.disabledDishIds` 统一决定，不在 `Dish` 内重复存储，避免两处状态冲突。
- 含肉末的麻婆豆腐按荤菜处理，蛋白质类型为牛肉。
- 纯素菜使用 `protein: 'none'`。
- 汤包含肉类时保留对应蛋白质类型，但不占用两道荤菜的名额。
- `ready` 且 `autoPlannable` 的菜品必须至少有一个食材，食材 ID 必须存在于食材库。
- 原菜单中的主食、小吃、水果和待确认菜品保留在菜库，但默认 `autoPlannable: false`。

### 10.4 设置

```ts
interface Settings {
  pantryIngredientIds: string[];
  blockedIngredientIds: string[];
  disabledDishIds: string[];
  repeatDays: number;
  maxSpicyDishes: 0 | 1 | 2;
  includeSoupByDefault: boolean;
  schemaVersion: number;
}
```

默认值：

```ts
const defaultPantryIds = BUILT_IN_INGREDIENTS
  .filter((ingredient) => ingredient.defaultPantry)
  .map((ingredient) => ingredient.id);

const defaultSettings: Settings = {
  pantryIngredientIds: defaultPantryIds,
  blockedIngredientIds: [],
  disabledDishIds: [],
  repeatDays: 7,
  maxSpicyDishes: 1,
  includeSoupByDefault: false,
  schemaVersion: 1,
};
```

`pantryIngredientIds` 在首次运行时由内置食材中的 `defaultPantry` 初始化，之后以用户设置为准。

### 10.5 已确认菜单

```ts
interface MealPlan {
  id: string;
  targetDate: string;
  dishIds: string[];
  historyWindowUsed: number;
  createdAt: string;
  updatedAt: string;
}
```

- `targetDate` 使用 `YYYY-MM-DD` 本地日期。
- `historyWindowUsed` 记录生成时实际使用的重复天数，可能是用户设置值、3 或 0。
- 同一个 `targetDate` 只保留一条已确认菜单；再次确认时覆盖原记录。
- `dishIds` 按“荤菜 1、荤菜 2、素菜、汤”的顺序保存。
- 是否包含汤由 `dishIds` 中是否存在 `role: 'soup'` 的菜品推导，不单独存储状态。

### 10.6 备份文件

```ts
interface BackupFile {
  schemaVersion: number;
  exportedAt: string;
  settings: Settings;
  customDishes: Dish[];
  customIngredients: Ingredient[];
  plans: MealPlan[];
}
```

### 10.7 AI 配置

```ts
interface AiConfig {
  enabled: boolean;
  baseUrl: string;
  textModel: string;
  visionModel: string;
  apiKey: string;
}
```

- `apiKey` 只保存在本机 IndexedDB 的独立 `aiConfig` 表中。
- `apiKey` 不进入 `BackupFile`，不写入日志、错误提示或导出文件。
- `baseUrl` 允许填写任意兼容 OpenAI Chat Completions 的地址；默认值不绑定具体服务商。
- `visionModel` 留空时禁用图片导入，其余 AI 功能仍可使用。
- AI 检查结果和导入草稿属于临时数据，不进入正式备份。

### 10.8 数据完整性

- 内置菜品和食材在构建时通过校验脚本检查。
- 任何菜品引用不存在的食材 ID 时，构建失败。
- 菜品 ID 和食材 ID 必须唯一。
- 食材名称在规范化后必须唯一。规范化包括去除首尾空格和统一常见别名。
- 内置数据不可被运行时修改，用户修改通过禁用和自定义数据实现。
- 本地数据库升级必须通过 `schemaVersion` 执行迁移，不能直接清空用户数据。

## 11. 采购清单生成

### 11.1 输入

- 一条已确认菜单。
- 菜单中所有菜品的食材 ID。
- 食材库。
- 用户常备食材设置。

### 11.2 生成步骤

1. 按菜单顺序取出每道菜的 `ingredientIds`。
2. 通过食材 ID 查询食材对象。
3. 按食材 ID 去重。
4. 排除 `pantryIngredientIds` 中的食材。
5. 按固定分类顺序分组。
6. 同一分类内按食材名称排序，保证每次显示顺序稳定。

去重必须基于 ID。即使两个食材名称相似，只要 ID 不同，也应保持区分；如果确认是同一食材，应在种子数据中统一为一个 ID。

如果菜品引用了不存在的食材 ID，不静默跳过，而是记录数据错误并阻止生成错误清单。

### 11.3 分类顺序

```text
肉禽蛋
蔬菜
豆制品
调料
主食
其他
```

分类为空时不显示该分组。

### 11.4 常备食材

内置食材的默认常备状态：

| 默认常备 | 食材 |
| --- | --- |
| 是 | 盐、食用油、生抽、老抽、醋、料酒、豆瓣酱、花椒、干辣椒、白糖、淀粉 |
| 否 | 葱、姜、蒜、鸡蛋、米、面、新鲜蔬菜、肉类 |

用户可以在设置中覆盖默认值。常备食材被排除后，清单页显示“已排除 N 项家里常备食材”，展开后可核对。

### 11.5 复制格式

- 标题使用目标日期，不使用容易过期的“今天”“明天”。
- 第一行列出菜单。
- 第二部分列出需要购买的食材。
- 只写名称，用中文顿号分隔。
- 没有需要购买的食材时，明确显示“无需采购”。

示例：

```text
10月28日晚餐：回锅肉、鱼香茄子、蒜蓉油麦菜

需要买：
五花肉、蒜苗、茄子、油麦菜、蒜
```

复制失败时，显示一个只读文本框并自动选中内容，用户仍可手动复制。

## 12. 页面与交互

### 12.1 信息架构

底部导航包含四个入口：

1. 安排。
2. 菜库。
3. 清单。
4. 设置。

历史记录从“安排”页的日期区域进入，不单独占用底部导航。

### 12.2 安排页

页面从上到下依次为：

- 日期切换和“安排明天”标题。
- 汤开关。
- 空状态或菜单卡片。
- 搭配检查。
- 主操作按钮。

空状态只保留一个主按钮“安排一下”，避免首次使用出现过多选项。

菜单卡片中：

- 荤菜卡片显示肉类标签。
- 每道菜显示辣度和口味。
- 已锁定的菜在换菜时显示锁定状态。
- 点击“换这道”只替换当前菜，不改变其他菜。
- 菜单下方提供“AI 检查这桌菜”按钮；按钮触发后才发起请求，不能自动调用。
- AI 检查结果包含问题列表、整桌建议和可替换菜品建议；每条建议都需要用户确认后才应用。

### 12.3 菜库页

- 顶部为搜索框和标签筛选。
- 列表按角色分组展示。
- 每道菜显示关键标签和“停用”开关。
- 右上角提供“新增菜”。
- 菜库顶部提供“图片导入菜单”入口；识别结果先进入草稿确认页，不直接写入菜库。
- `draft` 菜品显示“待完善”标记，并提供“AI 补全食材”和手动编辑入口。
- 支持筛选“只看 ready”“只看 draft”“只看可自动推荐”。
- 筛选结果为空时提示清空筛选条件。

### 12.4 清单页

- 顶部显示日期、菜单和“重新生成”入口。
- 中间显示待买食材分组。
- 底部固定“复制清单”按钮。
- 展开区域显示已排除的常备食材。
- 清单只读取已确认菜单，不允许在清单页单独增删食材，避免与菜单数据不一致。

### 12.5 设置页

- 常备食材使用可搜索的多选列表。
- 忌口食材使用可搜索的多选列表。
- 重复天数和最多辣菜数使用有限选项，不提供自由输入。
- AI 服务设置单独成组，包含启用开关、接口地址、文本模型、视觉模型、API Key、测试连接和清除 Key。
- API Key 输入框默认遮蔽；页面明确提示 Key 仅保存在本机且可能被浏览器扩展读取。
- 数据导出、恢复和重置放在页面底部。
- 重置操作必须二次确认。

### 12.6 AI 交互状态

- AI 未配置时，所有 AI 入口显示为“配置 AI 后可用”，不影响本地流程。
- 请求中显示加载状态，允许取消；超时时间默认 30 秒。
- 请求失败时显示可操作的原因：Key 无效、跨域失败、接口地址错误、模型不支持图片、触发限流或网络不可用。
- 任何 AI 失败都只影响当前操作，不回滚已确认菜单，不阻塞采购清单。
- AI 返回内容与界面语言一致，使用简体中文。

### 12.7 移动端要求

- 以 375px 宽度为最低适配基准，页面不能出现横向滚动。
- 主要按钮触控区域不小于 44px。
- 文本和背景对比度满足基本可读性要求。
- 标签不能只靠颜色区分，必须同时有文字。
- 复制按钮在 iOS Safari 和 Android Chrome 上都要可操作。
- 页面刷新后保留已确认数据；未确认草稿可以丢失。

## 13. 技术方案

### 13.1 技术栈

- React + TypeScript。
- Vite 作为构建工具。
- Tailwind CSS 作为样式方案。
- React Router 管理四个主页面。
- React Context + `useReducer` 管理应用状态，不引入额外状态库。
- Dexie + IndexedDB 保存本地数据。
- Zod 校验备份文件和本地数据升级。
- `vite-plugin-pwa` 提供 manifest、Service Worker 和离线缓存。
- Vitest + Testing Library 负责核心逻辑和关键交互测试。
- AI 调用统一封装为浏览器 `fetch` 客户端，不依赖特定厂商 SDK。
- AI 请求和响应使用 Zod 做结构校验，避免模型输出直接污染本地数据。

### 13.2 分层

### 13.4 本地存储

IndexedDB 包含以下表：

- `settings`：单条家庭设置。
- `customDishes`：自定义菜品。
- `customIngredients`：用户新增食材。
- `plans`：已确认菜单，按目标日期建立唯一约束。
- `aiConfig`：接口地址、模型和 API Key，单条记录，不进入备份。
- `aiCache`：可选的 AI 检查结果缓存，按请求内容哈希存储，不进入备份。

内置菜品和食材直接打包进应用代码，不复制到数据库。自定义数据通过 ID 与内置数据区分。

### 13.5 PWA 与离线

- 首次加载后缓存应用壳、内置菜库和静态资源。
- 离线时仍可生成菜单、换菜、查看已有清单和确认菜单。
- PWA 更新采用“下次启动生效”策略，避免用户正在安排菜单时页面被强制刷新。
- 核心流程不请求网络接口；只有用户主动触发 AI 功能时才联网。
- 断网时 AI 入口显示不可用，其他功能保持完整。

### 13.6 备份与恢复

- 导出使用 Blob 下载 UTF-8 JSON。
- 导入时先解析 JSON，再用 Zod 校验版本和字段。
- 先完成校验，再在单个数据库事务中覆盖用户数据。
- 任何校验失败都不修改现有数据。

### 13.7 部署

- 构建结果部署为静态站点。
- 必须使用 HTTPS 才能正常安装 PWA，`localhost` 开发环境除外。
- 首版不引入服务端环境变量、数据库或鉴权服务。
- AI 请求由浏览器直连用户填写的接口地址；如果服务商禁止浏览器跨域请求，AI 功能会明确报错，但不影响本地功能。

## 14. 初始菜库

初始菜库以用户提供的三张菜单截图为准，完整名单、原始来源和归类记录见 `docs/menus/2026-10-27-sichuan-family-dinner-menu-library.md`。

### 14.1 入库范围

- 原始条目共 190 条，去除 10 条完全重复项后为 180 道，全部进入初始菜库。
- 180 道中包括 98 道荤菜、47 道素菜、22 道汤、1 道待确认菜品和 12 道非推荐池条目。
- 非推荐池包括主食、小吃、甜品和水果，它们保留在菜库中，但默认不参与两荤一素推荐。
- 原图“凉菜”按实际主料重新归入荤菜或素菜；原素菜区中实际含肉或含蛋的菜品移入荤菜。
- 原“肉丝食谱”与猪肉区重复的 9 道菜只保留一条记录，新增的胡萝卜肉丝归入猪肉。
- 菜名或主料存在歧义的条目先标记为 `draft`，例如香酥藕盒、扇子骨、鲜椒朱毛肚，不能直接进入自动推荐。

### 14.2 ready 与 draft

- `ready` 表示菜名、角色、主蛋白质、辣度、口味和食材表均已复核，可以进入自动推荐。
- `draft` 表示菜品已入库，但食材或分类尚未完成，不能进入自动推荐。
- `autoPlannable: false` 用于主食、小吃、甜品、水果和待确认菜品；即使数据完整，也不会占用两荤一素名额。
- 首轮实现至少准备 20 道 `ready` 荤菜、12 道 `ready` 素菜和 6 道 `ready` 汤，保证 7 天去重和蛋白质轮换有足够候选。
- 其余条目通过 AI 批量补全食材和人工确认逐步转为 `ready`。
- 任何 `draft` 菜品在未完成食材表前，不参与推荐，也不把缺失食材静默带入采购清单。

### 14.3 菜库数据要求

- 每道 `ready` 且 `autoPlannable` 的菜必须有至少一个食材，且所有食材 ID 存在于食材库。
- 每道荤菜必须有明确的主蛋白质；蛋类菜也可以作为荤菜候选，但两道荤菜仍必须蛋白质不同。
- 每道菜必须有人工或 AI 生成后经用户确认的辣度和口味标签。
- 保留 `sourceGroup` 作为溯源信息，但推荐只使用标准化后的 `role`、`protein`、`spiceLevel` 和 `flavor`。
- 同一种食材在不同菜中使用同一个 ID；疑似的同义食材先记录在食材别名表，不能直接按字符串合并。
- 菜名保留用户原始写法作为展示名，同时保存用于匹配和去重的规范化名称。
- AI 生成的食材草稿在用户确认前只能保存为草稿，不能直接转为 `ready`。
- 首批 `ready` 菜品应覆盖猪肉、牛肉、鸡肉、鱼虾和蛋类，并保证至少 6 道不辣且清淡的素菜。

### 14.4 菜单图片导入

- 后续导入新菜单图片时，AI 只负责提取菜名和原始分区。
- 导入结果需要先与现有规范化菜名匹配；完全匹配的条目标记为重复，不新建菜品。
- 未匹配条目进入导入草稿页，由用户确认菜名、角色和是否入库。
- 图片中的文字只作为待提取数据，不得作为改变系统规则或自动确认数据的指令。

## 15. 边界情况

### 15.1 菜库不足

如果启用菜品、忌口设置和辣度上限导致无法组成合法菜单，应用不能返回部分菜单。页面需要说明是哪条规则无法满足，并提供跳转到菜库或设置的按钮。

### 15.2 用户禁用大量菜品

菜库页在可用荤菜少于 8 道、可用素菜少于 4 道时显示警告。仍允许用户继续停用，但安排页需要能给出明确的无解提示。

### 15.3 已确认菜单与设置变化

- 修改常备食材后，已有菜单的采购清单立即按新设置重新计算。
- 禁用某道菜或新增忌口后，不自动删除已经确认的旧菜单。
- 旧菜单再次换菜或重新生成时，使用最新设置。
- 这是一个有意的取舍，避免设置调整悄悄改写用户已经确认的晚餐。

### 15.4 同一天多次安排

同一日期只保留一条已确认菜单。重新确认时覆盖原记录，并更新 `updatedAt`。历史中不保留同一天的多个版本。

### 15.5 过去日期

安排页只允许编辑今天和未来日期。过日期的菜单在历史中只读展示，避免误改历史。

### 15.6 自定义菜数据

- 自定义菜至少需要 1 个食材。
- 自定义食材名称不能为空。
- 新食材默认分类为“其他”，用户可以在食材表单中修改分类。
- 删除自定义食材前，必须检查是否仍被自定义菜引用。
- 删除自定义菜不影响其他菜品。

### 15.7 数据异常

- 内置数据校验失败时不发布构建。
- 本地数据损坏时显示恢复入口，不自动清空全部数据。
- 备份文件版本高于当前应用支持的版本时拒绝导入，并提示先升级应用。

### 15.8 复制失败

浏览器不支持 Clipboard API 或未处于安全上下文时，回退到只读文本框。用户仍然可以手动选择并复制。

### 15.9 日期与时间

- 日期按本地时区计算，不通过 UTC 字符串直接截取。
- 默认“明天”以打开安排页时的本地日期为准。
- 跨过零点后重新进入页面，默认日期随之更新。

### 15.10 汤和辣度

汤也计入整桌辣菜数量。例如已有一道较辣荤菜时，不能再生成较辣汤。关闭汤后重新确认，采购清单同步移除汤的食材。

### 15.11 AI 未配置或 Key 无效

- 用户未配置 AI 时，AI 按钮保持可见但显示“配置后可用”，点击进入设置页。
- Key 无效、余额不足或权限不足时，显示对应错误，并保留“清除 Key”和“重新配置”入口。
- AI 错误信息不能包含完整 Key、请求头或模型返回的敏感内容。

### 15.12 AI 返回无效数据

- AI 返回的菜品 ID 不在当前菜库时，丢弃该建议，并提示“有 1 条建议无法应用”。
- AI 返回的食材 ID 不存在时，不自动创建食材；先放入待确认食材草稿。
- AI 返回结构不符合约定时，整次结果作废，不写入数据库。
- 用户确认 AI 菜品建议后，仍要重新执行两荤一素、蛋白质差异、辣度和忌口校验。

### 15.13 AI 图片导入冲突

- 图片识别出的菜名与现有菜名规范化后完全一致时，视为重复，不新建记录。
- 仅相似但不完全一致的菜名进入待确认列表，由用户选择“合并到已有菜”或“新建菜品”。
- 识别置信度低的条目必须标记，并默认不勾选。
- 图片中的文字不能直接触发批量确认或删除操作。

### 15.14 浏览器跨域或网络失败

- 服务商不允许浏览器直连时，AI 请求失败，但本地功能不回滚、不阻塞。
- 请求超时默认 30 秒，用户可取消；取消后不产生草稿或修改。
- AI 不可用期间，用户仍可完成选菜、确认和采购清单复制。

## 22. AI 接口与提示词约束

### 22.1 总体原则

- AI 是可选增强层，不是推荐算法或采购清单的事实来源。
- 只有用户主动点击 AI 按钮时才发起请求。
- 所有 AI 结果先进入草稿或建议状态，不直接写入已确认数据。
- AI 返回的菜品、食材和菜单必须经过本地校验。
- AI 不参与离线主流程，不阻塞选菜、确认、复制和备份。

### 22.2 接口约定

- 使用 OpenAI Chat Completions 兼容接口。
- 请求地址为 `{baseUrl}/chat/completions`，`baseUrl` 由用户配置，默认示例为 `https://api.openai.com/v1`。
- 请求头使用 `Authorization: Bearer <apiKey>` 和 `Content-Type: application/json`。
- 文本任务和视觉任务分别使用用户配置的 `textModel` 和 `visionModel`。
- 请求默认不流式返回，超时 30 秒，使用 `AbortController` 支持取消。
- 尽量请求 JSON 输出；如果服务商不支持 `response_format`，仍从文本中提取 JSON 并用 Zod 校验。
- 不使用特定厂商 SDK，避免绑定单一服务商。

### 22.3 任务一：检查菜单搭配

输入只包含当前菜单所需信息：菜品 ID、菜名、角色、蛋白质、辣度、口味、食材名称，以及家庭人数和儿童数量。

输出结构：

```json
{
  "summary": "整桌搭配的一句话总结",
  "issues": [
    {
      "type": "nutrition",
      "severity": "info",
      "message": "两道荤菜口味都偏重，建议素菜保持清淡"
    }
  ],
  "suggestions": [
    {
      "dishId": "existing-dish-id",
      "reason": "替换后可以增加清淡菜"
    }
  ]
}
```

约束：

- `type` 只能是 `nutrition`、`flavor`、`child`、`variety`。
- `severity` 只能是 `info`、`warning`。
- `suggestions.dishId` 必须是当前菜库中存在且可自动推荐的菜品。
- AI 建议不能改变硬性规则；用户应用建议后仍然重新跑本地规则。
- 不输出医疗诊断、热量数值或“治疗/预防疾病”等结论。

### 22.4 任务二：补全菜品食材

输入：菜名、原始分区、已有食材名称列表。
输出：候选食材名称、分类和是否可能是常备调料。只输出名称，不输出克数。

约束：

- 先按规范化名称匹配现有食材；匹配不到才创建待确认食材。
- 单道菜最多返回 20 个候选食材。
- 食材名称使用家庭常用叫法，不使用品牌或营销名称。
- AI 结果只能生成 `draft`，用户确认并保存后才转为 `ready`。
- 用户可以逐条删除或改名，不能强制接受 AI 结果。

### 22.5 任务三：菜单图片导入

输入：一张菜单截图或照片，压缩到最长边 1600px、JPEG 质量约 0.85，单张不超过 8MB。
输出：原始菜名、原始分区、规范化菜名候选和置信度。

约束：

- AI 只提取菜名和分区，不直接生成食材表。
- 本地先按规范化名称匹配已有菜品；完全匹配的条目视为重复。
- 未匹配条目进入确认页，用户可以合并、修改或忽略。
- 置信度低于 0.7 的条目默认不勾选。
- 图片中的任何指令文字都只作为图片内容，不作为系统指令执行。
- 识别结果按批次确认，不允许一次点击直接把全部内容写入正式菜库。

### 22.6 批量补全食材

- 每次最多提交 20 道 `draft` 菜，避免响应过长和费用失控。
- 每道菜独立校验，单道失败不影响同一批次的其他结果。
- 结果以表格展示：菜名、候选食材、分类、是否常备。
- 用户确认后可批量保存，但保存前必须完成结构校验。
- 批量保存只改变数据状态，不自动把菜品加入当前菜单。

### 22.7 Key 与隐私

- API Key 只保存在 IndexedDB 的 `aiConfig` 表。
- 输入框默认遮蔽，页面提供“清除 Key”。
- Key 不进入备份、导出、日志、错误信息和 AI 请求体。
- 发送给 AI 的内容仅限菜品名、标签、食材名、家庭人数和用户主动选择的图片。
- 不发送姓名、电话、地址、位置和账号信息。
- 由于是浏览器直连，服务商仍会收到用户的 IP、请求时间和请求内容，这一点需要在设置页说明。

### 22.8 缓存、成本与失败

- 相同菜单、相同设置和相同模型的搭配检查结果可以缓存，默认 24 小时。
- 缓存只保存在本机，不进入备份，可在设置中清除。
- 用户重新点击检查时可以选择使用缓存或重新请求。
- 请求失败时保持上一次有效结果，不写入半成品数据。
- 遇到 401、429、CORS、超时和模型不支持图片时，给出具体可操作提示。
- AI 不自动重试多次，避免产生不可控费用。

### 22.9 AI 验收

- 未配置 Key 时，所有核心流程可完整使用。
- 401、429、超时和跨域失败均不改变本地数据。
- AI 建议中的未知菜品 ID 被丢弃。
- AI 生成的食材不会自动变成 `ready`。
- 图片导入不会绕过重复检测和人工确认。
- 备份和日志中不出现 API Key。
- 用真实 Key 完成一次搭配检查、一次食材补全和一次图片导入，作为手动验收项，不作为自动化测试依赖。
